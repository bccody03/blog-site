A. Technical

T22 The "gated" chapter is a public, crawlable, indexable PDF Critical

Now — measured 
$ curl -I https://blakecody.com/chapter-1.pdf
  200 · 61,389 bytes · application/pdf

PDF internals: producer "ReportLab PDF Library", /Font present,
               embedded IBM Plex Serif, real text operators
               -> the full chapter text is machine-extractable

robots.txt:    User-agent: *
               Allow: /                nothing excludes it

book.html:     <div class="chapter-done" id="chapter-done" hidden>
                 <a id="chapter-dl" href="chapter-1.pdf" download=…>
               a plain crawlable link, no rel="nofollow".
               `hidden` hides it from readers, not from crawlers.
Why it matters
  1. The gate does not gate anything. The URL is guessable, publicly served, and linked from your own markup. Anyone who wants the chapter without giving an email already can — and the email is the entire purpose of the gate.
  2. The PDF competes with this page in search. Google indexes PDFs as standalone results. A query matching the chapter's opening — and that opening is distinctive, emotional prose that could match real queries — can return chapter-1.pdf instead of book.html. You would be outranked by your own lead magnet, on the one page that carries the signup form.
  3. You cannot fix it with noindex. Meta robots tags do not exist in a PDF, and the X-Robots-Tag HTTP header is not settable on GitHub Pages. The usual answer is unavailable to you.
Fix — decide what you actually want first

Option A — the email matters most. Keep the gate and make it hold:

1. Move and rename the file to something unguessable
   /c/8f3a2b1c4d/aligned-chapter-1.pdf

2. Remove the static href; set it only after a successful submit
   <a id="chapter-dl" href="#" download="Aligned-Chapter-1.pdf">…</a>
   dl.href = CHAPTER_PATH;   // in the submit success branch

3. robots.txt
   Disallow: /c/

This is not airtight — nothing served from a static host can be — but it closes the search-result leak and the guessable filename, which are the two ways this actually fails in practice.

Option B — reach matters more than the email. Publish the chapter as HTML on this page. Then:

  • The content is indexable, on your domain, in your design, and it is yours — not a PDF result with no navigation and no signup form.
  • Given C4 (nothing on this domain ranks because almost nothing is on it), a full chapter of real prose in HTML would be the single strongest piece of indexable content on blakecody.com. It is around 3,000 words of distinctive first-person writing on a subject people search for.
  • The signup moves below the chapter as a soft ask — "if this was useful, here's where the rest lives" — which converts worse per-visitor and better per-reader.

Minimum, today, whichever you choose later: add Disallow: /chapter-1.pdf to robots.txt and remove the static href. That is ten minutes and stops the bleeding.

My read: you are early enough that reach is worth more than a list. Option B, and revisit when the traffic exists to trade.

T23 No structured data, on the one page where Book schema belongs High

Now

Measured: 0 JSON-LD blocks on book.html. Meanwhile index.html declares a Book node for Aligned whose url points here, and articles.html now has CollectionPage + BreadcrumbList. The book page is the only content page left with nothing.

og:type is correctly set to book ✓ — but none of the book: Open Graph properties are present.

Fix

Reuse the @id the homepage already defines, so the two declarations reconcile into one entity rather than describing two different books:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@graph": [
    { "@type": "Book",
      "@id": "https://blakecody.com/#aligned",       // same id as the homepage
      "name": "Aligned",
      "alternateName": "Aligned: Lead with Love, Live with Intention",
      "author": { "@id": "https://blakecody.com/#person" },
      "inLanguage": "en",
      "abstract": "A field guide for anyone rebuilding after heartbreak — three
                   parts: decoding love, building yourself, living with intention.",
      "url": "https://blakecody.com/book.html",
      "image": "https://blakecody.com/book-cover.jpg"   // see T24
    },
    { "@type": "WebPage",
      "@id": "https://blakecody.com/book.html#webpage",
      "url": "https://blakecody.com/book.html",
      "isPartOf": { "@id": "https://blakecody.com/#website" },
      "about":    { "@id": "https://blakecody.com/#aligned" } },
    { "@type": "BreadcrumbList",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "Home",
          "item": "https://blakecody.com/" },
        { "@type": "ListItem", "position": 2, "name": "The Book" } ] }
  ]
}
</script>

Plus the OG properties for a book:

<meta property="book:author" content="https://blakecody.com/" />
<meta property="book:tag" content="relationships" />
<meta property="book:tag" content="personal growth" />
One caution

Do not add offers, an isbn, a datePublished or an aggregateRating. The book is unpublished — your own copy says "I'm in the process of becoming an author" — and fabricating those is both a structured-data violation and exactly the kind of thing that costs you the trust this page is built on. If you want the status in the graph, "bookEdition" can be omitted and the abstract can say it plainly. Add offers the day there is something to buy.

Why it matters
  • The Book schema in T23 wants an image. Without one the entity is thinner than it needs to be.
  • Shares of this page fall back to the generic site card, so a link to your book looks identical to a link to your privacy policy.
  • Image search returns nothing for the book.
  • A book page with no picture of the book asks a stranger to take it on faith.
Fix

You need cover art. It does not have to be a finished publisher's jacket — a typographic treatment in Fraunces on your existing cream-and-rust palette, rendered at 1400×2100, would do everything required here and cost an afternoon. Export a 1200×630 variant for og:image on this page specifically, so a shared book link shows the book.

Until that exists, the honest interim is a pull-quote block from the excerpt set in large Fraunces — something for the eye to land on that is not a stock photograph.

Both H3s are interface chrome. Nothing in the document structure marks the excerpt, and the actual chapter title — "Grieving a Ghost — The Person You're Mourning Never Existed", which is the most distinctive, most searchable line on the page — sits in a <p class="excerpt-chapter">.

Fix 
<h1 class="book-title">Aligned</h1>
  <h2 class="excerpt-label">Read the opening of Chapter 1 — free</h2>

Measured: 371 static words of genuine first-person prose — more than the homepage and the archive combined before their rewrites. Nothing in this report asks you to change the voice.

One structural note, offered as a suggestion rather than a finding. The page opens with "I'm in the process of becoming an author — and honestly, it still feels surreal to write that." C26 The gate is honest — verified, and worth protecting Pass

I checked specifically for cloaking, because email gates are a common way sites drift into it. Measured:

document.getElementById('excerpt-more')  →  null
hidden chapter text in the DOM           →  none

What Google receives is exactly what a reader receives: three paragraphs and a form. There is no hidden remainder served to crawlers and withheld from people. That is the correct implementation and it should stay that way if you extend the excerpt under C24 — add real visible words, never a hidden block revealed by script.

Also correct on this page: type="email", autocomplete="email", required, a real <button type="submit">, and a visible success state. The form itself is well built.

C. Tracking & measurement

K14 Chapter downloads are undercounted, and you cannot tell by how much High

Now

track("chapter-request", "Chapter 1 requested") fires on successful form submit ✓ — correctly implemented in pass 1. But it is measuring one of three paths:

Path to the chapterTracked?
Form submit → auto-download✓ yes
The fallback link ("tap here to download the PDF") after a failed auto-download✗ no
Direct hit on chapter-1.pdf — from search, a shared link, or a guess (T22)✗ invisible — never touches your JS at all
Why it matters

Whatever number GoatCounter shows you for chapter-request is a floor, not a total, and the size of the gap is exactly the size of the T22 leak. If you read that number as "chapter reads" you will underestimate demand and over-estimate the gate's value at the same time.

Fix 
// the manual fallback link
document.getElementById("chapter-dl")?.addEventListener("click", () =>
  track("chapter-download-manual", "Chapter PDF, manual link"));

Direct PDF hits cannot be measured by client-side analytics at all. Under T22 Option A, routing through /chapter?t=… gives you a measurement point and a gate in the same move. Under Option B the question dissolves, because the chapter becomes a page with a pageview.

Until then: when you read chapter-request, read it as a floor.

K15 You track the submit but not the impression, so the rate is unreadable Medium

There is no event for a reader reaching the gate. Without that denominator, "12 chapter requests this month" could mean a 60% conversion rate on a page nobody finds, or 2% on a page that works. Those two situations call for opposite responses — one says promote the page, the other says fix the gate — and you currently cannot tell them apart.

Fix 
const gate = document.getElementById("excerpt-gate");
if (gate && "IntersectionObserver" in window) {
  const io = new IntersectionObserver((entries) => {
    if (entries.some((e) => e.isIntersecting)) {
      track("gate-viewed", "Chapter gate seen");
      io.disconnect();                // once per pageview
    }
  }, { threshold: 0.5 });
  io.observe(gate);
}

Two events, one ratio. That ratio is what tells you whether C24's longer excerpt actually helped, which is otherwise a guess.
