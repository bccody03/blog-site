A. Technical

T16 Pagination creates no URLs — posts 10 and older have no address Critical

Now

articles.html sets data-page-size="9", and renderPagination() builds the controls as buttons, not links:

html += `<button class="page-btn page-num..." data-page="${i}"...>${i}</button>`;

I rendered the page with a 23-post feed and clicked through to page 2. Measured:

pager elements:  BUTTON ←  BUTTON 1  BUTTON 2  BUTTON 3  BUTTON →
                 href: null on every one

after clicking page 2:
  location.href    unchanged   (still /articles.html)
  location.search  ""
  location.hash    ""
  history.length   2           (unchanged — no history entry pushed)
  content          posts 10–18 now displayed
Why it matters

Four separate consequences, all from the same cause:

  1. Crawlers never see past post 9. Googlebot renders JavaScript but it does not click buttons. There is no URL for page 2, so there is no way for any crawler to reach posts 10 and older. On a page titled "Every essay and dispatch", most of the essays are invisible.
  2. Nothing beyond page 1 can be linked or shared. No reader can send someone "the page with that essay from March".
  3. The back button is broken. No history entry is pushed, so pressing Back from page 3 leaves the archive entirely instead of returning to page 2.
  4. No rel="next"/rel="prev", because there is nothing to point them at.
Fix — the interim version

Make the pager real links with a query parameter, and read it on load:

// renderPagination — links, not buttons
html += `<a class="page-btn page-num${i === cur ? " active" : ""}" 
          href="?page=${i}" data-page="${i}">${i}</a>`;

// on click, intercept and push state instead of reloading
history.pushState({ page: p }, "", p === 1 ? "articles.html" : "?page=" + p);

// on load, honour the parameter
const start = parseInt(new URLSearchParams(location.search).get("page"), 10) || 1;
renderPage(start);

// and handle Back
addEventListener("popstate", (e) => renderPage((e.state && e.state.page) || 1));

Then add <link rel="canonical" href="https://blakecody.com/articles.html?page=N"> per page — or, simpler and better for a small archive, keep the canonical on page 1 and add rel="next"/rel="prev".

Fix — the version that actually solves it

For an archive of this size, paginating at all is the wrong call. Nine per page across 20–30 essays gives you three pages, none of which a crawler can reach, in exchange for saving a reader a scroll. Either:

  • Show all posts on one page — set data-page-size="0", delete the pager. One URL, every essay crawlable, no history problem, no canonical question. This is a one-character change and it fixes the whole finding.
  • Or do C4 and give each essay its own URL, at which point the archive is a real index and pagination is a genuine paging concern rather than a content-hiding one.

Given that you are likely to do C4 eventually, I would set data-page-size="0" today and not build the pushState machinery at all.

T2-A The archive serves 50 words and an empty div High

Now

Measured static text in <body>: 50 words — navigation, an H1, one sentence, "Loading…", the subscribe block and the footer. Rendered after JS: 296 words, 9 cards.

<div class="state" id="state">Loading…</div>
<div class="post-list" id="post-list" data-page-size="9"></div>
Why it matters

This is the same root cause as T2 on the homepage, but the consequence is worse here. The homepage has an Explore grid, an app block and a subscribe section that exist in HTML regardless. This page's entire reason to exist is the list, and the list is not in the HTML. To a crawler that does not run JavaScript — Bing, and effectively every AI crawler — articles.html is a 50-word page that says "Loading…".

Fix

Same build-time prerender proposed in T2: a scheduled GitHub Action fetches the Substack RSS and writes the cards into the HTML. Interim, add a <noscript> list of the most recent titles and links so there is something real in the markup.

T18 No structured data on this page High

Now

Measured across the site:

PageJSON-LD blocks
index.html1 — a five-node graph: Person, WebSite, Book, SoftwareApplication, WebPage ✓
articles.html0
book.html, reflect.html, about.html, privacy.html, 404.html0 (covered in their own reports)

The homepage schema was implemented well. It just did not travel to the other pages.

Fix

An archive wants three things: what kind of page it is, what it lists, and where it sits. Add before </head>:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@graph": [
    { "@type": "CollectionPage",
      "@id": "https://blakecody.com/articles.html#webpage",
      "url": "https://blakecody.com/articles.html",
      "name": "Essays by Blake Cody",
      "description": "Every essay and dispatch on discipline, love and living with intention.",
      "isPartOf": { "@id": "https://blakecody.com/#website" },
      "about":    { "@id": "https://blakecody.com/#person" },
      "inLanguage": "en-US" },
    { "@type": "BreadcrumbList",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "Home",
          "item": "https://blakecody.com/" },
        { "@type": "ListItem", "position": 2, "name": "Articles" }
      ] }
  ]
}
</script>

Note the @id references reuse the nodes the homepage already defines — that is what makes it one graph rather than five disconnected ones.

Then add an ItemList of the posts, generated alongside the cards in T2-A's prerender step. Generating it client-side is possible but pointless: if JavaScript has to run to produce your schema, the crawlers that most need the schema will not see it.

The BreadcrumbList also gives you the breadcrumb display in search results, and this page already has the visual breadcrumb to match it — <p class="eyebrow"><a href="/">← Home</a></p>.

T17 How deep does the feed actually reach? Medium

loadFromSubstack() requests count=50 from rss2json, which is generous. But the ceiling is not rss2json — it is Substack's own RSS feed, which typically serves only a recent window (commonly the last ~20 posts) regardless of what you ask for.

If that is the case here, then "Every essay and dispatch, newest first" is not true: essays older than the feed window are silently absent, with nothing on the page to say so.

Verify

I could not test this — api.rss2json.com is blocked by this environment's egress policy. Count the cards on the live archive and compare against your Substack archive page. If they differ, you have a content gap.

Fix if confirmed

The prerender pipeline (T2-A) solves it permanently: fetch on a schedule and accumulate into a local JSON file rather than replacing it, so posts that fall out of the feed window stay in your archive. This is another reason to move the fetch to build time.

T19 No RSS link on the page where it belongs most Low

index.html now carries <link rel="alternate" type="application/rss+xml"> ✓. articles.html does not — and the archive is exactly where a reader or a feed reader looks for it.

<link rel="alternate" type="application/rss+xml"
      title="Blake Cody on Substack" href="https://bccody.substack.com/feed" />

Add it to every page, or at minimum to this one. Consider a visible "Subscribe by RSS" link next to the pager too — the audience for a personal essay archive skews toward people who still use feed readers.

T20 og-image.png now returns 404 Low

Verified live: og-image.jpg → 200 (46 KB) ✓, og-image.png → 404.

The meta tags were all updated correctly, so new shares are fine. But any previously shared link whose preview was cached against the old PNG, and any external page referencing it, now points at a missing file.

Fix

GitHub Pages cannot issue a redirect for a static file, so the fix is simply to leave a copy: keep og-image.png in the repo alongside the JPEG. It costs 46 KB of repository space and nothing at runtime, since no page references it any more.

T21 CONFIG.maxPosts is now dead config Low

maxPosts: 12 is read only by postLimit(), which applies when a list has no data-limit. The homepage sets data-limit="3"; this page uses data-page-size="9" and paginates the full array. So maxPosts currently affects nothing.

Harmless today, misleading later — someone editing this file will reasonably assume changing it does something. Either delete it, or wire it to count= in loadFromSubstack() where a post cap actually belongs.

C18 No topic grouping — and you already have the taxonomy Medium

Now

The archive is a single reverse-chronological list. There are no categories, no tags, no topic pages. For search, that means there is no page on the site targeting any specific subject — the archive is one URL competing for everything at once, which in practice means it competes for nothing.

The thing you already built

reflect.html has topic chips — .cat elements with data-cat attributes — that let a reader pick a subject before writing to you. That taxonomy already reflects how you think about your own subject matter. It is the obvious grouping for the essays too.

Change to
  • Short term: add filter chips to the archive using the same categories, matched against post titles/tags from the feed. Client-side filtering, no new URLs — useful for readers, neutral for SEO.
  • Real version (needs C4): once essays live on your domain, each topic becomes a page — /topics/discipline, /topics/intention — with an intro paragraph and the essays beneath it. These are the pages that would actually rank for non-brand queries. The homepage never will; the archive alone probably will not; topic hubs are the standard answer and they work.

C19 One sentence of body copy on the whole page Medium

"Every essay and dispatch, newest first." is the entire prose content of the archive. Nothing frames what the essays cover, who they are for, or why someone should start reading.

Change to

60–100 words between the H1 and the list. Not keyword filler — a real short introduction: what you write about, roughly how often, what a new reader should start with. Link two or three specific essays by name inside that paragraph. That gives you internal links with descriptive anchor text, which the card grid currently does not provide, and it gives Google a passage that describes the collection.

C. Tracking & measurement

K10 Pagination clicks are not tracked — you cannot tell if page 2 is ever reached Medium

Now

renderPage() and the pagination click handler contain no track() call. The K1 implementation covers outbound clicks, chapter requests, reflections and feed errors — all correct — but not this.

Why it matters

This is the number that decides T16. If nobody ever clicks past page 1, pagination is pure cost — it hides content from crawlers and buys nothing — and you should set data-page-size="0" and be done. If people do page through, that tells you the archive is being browsed rather than bounced from, which is worth knowing on its own.

Fix 
// inside the pagination click handler, after parsing p
track("archive-page-" + p, "Archive page " + p);

One line. Give it two weeks and the answer to T16 is a fact rather than a judgement call.

K11 Card clicks do not record which card Medium

Now 
const where = a.id ? a.id : a.closest(".post") ? "card" : "other";
track("click-substack-" + where, "Substack click");

Every one of the nine cards on every page fires the identical click-substack-card event. You can see that the archive sends traffic to Substack; you cannot see whether readers click the newest post, scan to something further down, or hunt for a specific title.

Fix 
const card = a.closest(".post");
if (card) {
  const idx = [...card.parentElement.children].indexOf(card) + 1;
  track("click-substack-card-" + idx, "Substack click, position " + idx);
}

If clicks cluster on position 1, the archive is functioning as "show me the latest" and the homepage's three-post list is doing the same job — consider whether you need both. If they spread down the list, readers are genuinely browsing, which argues for C18's topic grouping and against pagination.
